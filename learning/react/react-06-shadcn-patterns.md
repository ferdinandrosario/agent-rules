## The thesis: vendored source, not a dependency

`web/src/components/ui/*` is **owned code** generated by the shadcn
CLI — Rails analogy: scaffold output you edit, vs a gem you configure.
That's why the rules treat it as source ("editing `ui/*` from inside a
feature folder" is forbidden; variants extend the primitive's own
`cva` map) and why there's no `@shadcn/components` runtime dep — only
the `shadcn` devDep that generates files.

## The three mechanisms to read fluently

1. **CVA variant maps**
   ([`button.jsx`](../../../web/src/components/ui/button.jsx)): a typed
   lookup table — `variant` (default/outline/secondary/ghost/
   destructive/link) × `size` — compiled to class strings. Adding a
   variant = adding a map entry, not a new component (full convention:
   ui.md "Variant conventions").
2. **`cn()`** (`personal_manager/web/src/lib/utils.ts`) =
   `clsx` (conditional join) + `tailwind-merge` (conflict resolution,
   **last wins**) — which is why a caller's `className` can override a
   primitive's default padding without `!important`.
3. **Composition via Radix `asChild`/Slot**: render *as* the child
   instead of wrapping it — `<Button asChild><Link/></Button>` yields
   one element with Button's classes and Link's behavior. This is the
   composition-over-configuration trade running through the whole kit.

The layer above the primitives is app-owned composites —
`entity-tab.jsx`, `entity-form-dialog.jsx` — which *compose* ui/
pieces and are where feature-facing behavior lives.

## Why no new-variant exercise shipped

The track's draft exercise (add a `destructive-outline` button
variant) violates two house rules with no current consumer: variants
are added when a screen needs one (no dead code), and `ui/*` edits
follow ui.md's conventions when that day comes. The R1 retry button
exercised the real path instead: *consume* an existing variant
(`outline`) from a feature screen.
